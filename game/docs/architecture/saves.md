# Saves

## Storage

- Saves and run logs live in IndexedDB, in one database per save scope named like the old save key. The `saves` store holds one save envelope per slot. The `log` store holds run log records by run id and sequence number. `src/three/save-db.ts` owns both.
- IndexedDB stores objects as they are, so a save is a plain object, not a JSON string. Each write is one transaction, so it lands whole or not at all. Its quota is a share of the disk, not the 5 MB of local storage.
- `SaveSlots` mirrors every save in memory, so the game reads and writes slots at once. A write goes on to the database in the background. A failed write shows a note in the HUD and goes to the crash handling. Load and New game wait for every pending save and log write before they reload the page.
- The browser may close the database connection on its own, for example Safari after the tab sits in the background. `save-db.ts` then reopens it on the next read or write and retries that call once. A write that still fails shows the save note.
- Boot asks the browser for persistent storage, so it does not evict saves under disk pressure. A refusal leaves saves best-effort, as local storage was.
- Older builds kept saves in local storage. Boot moves each of them into the database and then deletes its local storage key. A local storage save replaces a database slot only when its `savedAt` is newer, since a tab of an old build may still write there. A save that did not parse moves as its text, and load reports it as unreadable.
- Boot retries a refused IndexedDB open once. An open that does not answer in 5 seconds counts as refused, and a connection that opens after that is closed. After a second refusal it keeps saves in local storage under the old keys and the run log in memory for the session, with a console warning. The next boot where IndexedDB opens moves them in.

## Slots and boot

- `src/three/save.ts` stores the world in a save envelope `{ format, steps, quests, savedAt, runId, world }` and restores it on boot. `quests` holds the revision of every quest the save was made under, a fact about the content and not part of `World`. An envelope without it reads as revision 1 everywhere.
- `loadWorld()` returns the repaired world. The repaired world is not written at load. The stored save stays as it was until the next save, so every load repeats the same repair and the original stays downloadable.
- Load repairs drift and never throws on it. Drift is a save that still makes sense but names game data that changed since: a rebaked map, a removed part, chassis, good, template, trait, faction, perk, shop, site, site event, wave template, note, state kind or dialogue node, a lowered maximum, a moved part footprint, or a driver name outside the name lists. `repairMap()` in `src/sim/map-repair.ts` moves a Roaming world onto a new bake of Icarus. `repairContent()` in `src/sim/save-repair.ts` fixes content drift in place. An open quest whose checkpoint no longer restores is reset like a quest whose revision rose. The repair is silent. It keeps what the player held wherever it can: a part that no longer fits the player's truck goes to storage, goods that no longer fit are sold at their value, and a contract that a rebake ends lapses as in play. Only what the game no longer has is dropped. Any other throw during load becomes a `SaveError`, so a missed drift reaches the save screen and never the crash screen.
- Load checks that the world fits this build before the game sees it. `src/three/save-schema.json` describes `SavedWorld` in `src/three/save-fit.ts`, the shape `saveOf()` writes, field by field. `npm run save:shape` builds it with the type checker of the game's TypeScript 7, from `typescript/unstable/sync`. String-literal types become plain strings, so drift stays the repair's job and new content never changes the schema. A tag stays exact: a property that every member of a union of object types holds with a different literal, like a contract's `kind`. Before the repair, `dropUnknownKeys()` removes keys the schema does not hold, since saves of other branches and old steps carry keys no one can list ahead. After the repair, `checkSavedWorld()` runs on `saveOf()` of the loaded world. A missing field, a wrong type, an unknown key or a number that is not finite is `SaveError('invalidWorld')`, and its detail names the path, like `world.crimes: missing`. The carry runs the same check on the world it builds.
- `writeSave()` runs the check before it stores. A misfit there is a game bug. It goes to `SaveSlots.onError`, the failed-save route, and the slot keeps its old save. A thrown `SaveError` is kept for a save that contradicts itself. `save-rescue.test.ts` loads every shipped Roaming save and plays it for 20 turns, which catches drift no repair covers yet.
- `src/three/save-slots.ts` owns the slots: `CONFIG.saveSlots` manual slots, the Autosave (every `CONFIG.saveTurns` completed turns and after each command in town) and the Day start autosave (the first turn of each game day). The Save and Load panels in `src/ui/save-panel.ts` pick a slot. The Save and Load entries of the Menu button in the top right open the panels.
- Load and a confirmed New game leave a boot request in session storage and reload. Boot reads the request and removes it. Without one, it shows the start menu, `chooseStart()` in `src/ui/save-screen.ts`, after the map and the slots are open. Its Continue loads the newest save by `savedAt`, names that save in a caption under the button, and is off with no save. Its Load opens the shared save list (`SaveList` in `src/ui/save-panel.ts`), and a pick boots that slot in the same page with no confirm. Its New game opens the New game screen, whose Start writes a request and reloads. In dev, `?play` skips the menu: boot loads the newest save, or starts a new game without the intro when there is none.
- Boot's New game runs `clearGame()`, which deletes the autosaves and everything else the run keeps in storage but not the manual slots or sound settings, then writes the Autosave at once. Later unsaved changes are lost on reload.
- World setup: New game opens the New game screen in `src/ui/new-game.ts`, and only its Start writes a boot request. A new game request holds the picked mode and world settings as JSON, and `takeBootRequest()` removes it before it checks them with `parseSetup()`, so it is used once even when it is bad. Boot builds the world with that setup and saves it at once. The request also holds `intro`, true unless the player switched on Skip the intro. `takeBootRequest()` throws on a request without it. Load and rescue keep the valid saved settings, and reset the bad ones with `repairSetup()`. A setup that is no object or names an unknown mode is a `SaveError` that leads to the save screen. `src/sim/settings.ts` owns the setup, and [world settings](../wiki/mechanics/world-settings.md) has the rules.
- `world.chaosHighway` is the saved Chaos Highway run, or null in Roaming: its `window`, the facts of the window's two outposts (milestone, stock, paid), the current stretch's groups, the run totals `earned` and `wrecks`, and the `hauler` facts. Its land, scenes, ramps, forts, pads and props are derived from the seed and the window, so none of them is saved. An outpost's `paid` flag and the window are what stop a reload from paying twice.
- `mapFor(saved, icarus)` in `src/three/save.ts` picks the map of a save on boot, load and rescue: Icarus for a Roaming save, and `highwayMap(seed, window)` for a Chaos Highway save, whose hash must equal the saved one. A Roaming save on an older bake of Icarus loads onto the current one through `repairMap()`. A Chaos Highway save with no run or on a changed highway is a `mapChanged` `SaveError`, and one on Icarus is `otherMap`. The rescue puts a run back at the start of its stretch, and a save with no run gets a fresh run. `newMapFor()` in `src/sim/highway.ts` picks the map of a new world.
- Driving on from a paid outpost moves the world to the next window. `GameSaves.changeMapIfMoved()` sees the new map hash after the command and before a turn plays, and only with the `roadOpened` event in that world, writes the Autosave, and leaves a road boot request `{ slot: 'auto', reason: 'road' }` before it reloads. Boot loads the Autosave on its new window under the step "Opening the road north". The arrival's payout line was already in the log when the player parked. It throws while saves are held, since the reload would lose the turn, and on a moved map with no road opened.
- A save holds only what load cannot rebuild. Load takes the terrain and the baked props from the map file, rebuilds the player's visible tiles, contacts and seen clouds with `refreshVision()`, and starts trails, events and removed vehicles empty, since they only animate the last turn. A broken prop is saved as its id and turn, and one the map no longer holds as a breakable prop stands again. An open quest is saved as its last checkpoint, and load restarts it there, as [Quests](quests.md#saves) describes.
- `player.explored` is saved as a base64 bitset.
- A save records the map file's hash, or the highway hash, and does not load on another map.
- A build with `SAVE_SCOPE` set stores its saves in its own database, so builds served from one site keep separate saves.
- A dead world is never saved.
- A write the browser refuses (a full disk quota) leaves the slot's old save in the database and the new one in the memory mirror. The game notes "The game could not save" in the log and reports the error. Boot and rescue continue unsaved. Nothing is cleared to make room.

## Run log

- `src/three/run-log.ts` writes the run log. `src/sim/run-stream.ts` holds the pure writer it uses, and the recorder uses the same writer. The log never replays the game and never feeds the sim.
- The log is a stream of what the player's view held, like a multiplayer game's network stream. A truck enters the view with its full description. Each turn after that sends only what changed. Then the truck leaves.
- A truck is in scope while the player owns it (faction `player`), while the player sees it, and in a turn where an event ties it to a player truck, such as a shot from out of sight. Scope never reads the mode or the map id.
- Every line has its turn. These are the line kinds.
- `session` holds the run id, version, seed, mode, settings and map hash. Its `from` says how the session began: `new`, a slot id, `day`, `resync` or `record`.
- `player` holds money, XP, ranks, perks, storage and switches. After the keyframe it holds only the fields that changed.
- `enter` holds the id, template, faction, chassis and driver. It also holds every part with health, goods, position, heading, speed, order, gun and utility orders, goals, states, fuel, supplies and money.
- `moves` holds `[id, x, y, heading, speed]` for each truck that moved.
- `change` names one truck and holds only the fields that changed.
- `leave` names one truck and the reason: wrecked, knockedOut, despawned, window, gone or unseen. Gone means the truck no longer exists and no event says why. Unseen means it still exists but is out of view.
- `event` is one game event, or a merged group of shots or collisions.
- A `session` line is followed by a `player` line and an `enter` for every truck in scope, so any session reads on its own. It is written at New game, at each load and at each day start.
- An `event` line is any event that names a truck in scope, plus the player's own outcomes. A turn's shots from one shooter at one target merge into one line with the weapons, rounds, hits, damage per part and the parts they disabled. A turn's collisions between two trucks merge the same way. Practice, arrivals, spawns, talk, weather and other clutter stay out.
- Positions are world positions: map position plus the map's origin. Icarus has origin zero. The highway's origin moves with each window, so a truck keeps one position across a window move. Positions are to 0.1 tile, angles to whole degrees and part health to whole percent.
- Player decisions have no command log. Every decision shows as a change on a player truck or on the player: an order, a gun order, a switch, a purchase.
- The game hands the log every world it takes: after each command, at the start of each turn's playback and after a talk. The log writes each world once and each events array once. It diffs against the last line it wrote, so a world that shares events with the last one adds no event twice. The database numbers records inside the write, so two tabs on one run never take the same number.
- The turn that moves the highway window is logged before the page reloads. The next boot starts a new `session` at the same turn.
- The log is append-only. After a load the turns can run backwards. A reader drops the records after the load's turn that came before it. `npm run run:timeline` does this.
- Every line carries `sid`, a session id that is new at each boot of the log. Two tabs on one run write two streams with two session ids, and their lines interleave in the store. Each stream starts with its own keyframe, so a reader rebuilds state per session id and never mixes deltas from two tabs. `replayBySession` and `npm run run:timeline` do this.
- A write that fails leaves the log without lines the stream already counted as written. The next world after a failed write starts a new `session` keyframe with `from` set to `resync`, so no delta sits on a base the log never stored.
- A load or a new boot has a new session id. The reader drops the earlier session's records after the load's turn only when that session wrote nothing after the load began. A session that goes on writing is another tab, and its records stay.
- A run that began on an older build keeps its old records, such as `start`, `loaded`, `day` and `change` without a truck id, before the first `session` line. `npm run run:timeline` skips them and says how many.
- The Save panel's Export run log button downloads the run as JSON Lines: a header with the run id, game version, seed and map hash, then one record per line. Export save downloads the current game as a save envelope in JSON.

## Versions

A save records its format, `SAVE_FORMAT` in `src/three/save.ts`. The Help entry of the Menu shows the game version, which `src/version.ts` builds from the save format and git as `SAVE_MAJOR.minor.commits+hash`, so nobody edits it by hand. Load migrates an old save to the current format, as Save migrations in `CLAUDE.md` describes. Each quest also has a revision, from its `# revision:` tag. Load resets a quest whose revision rose since the save, and the quests whose progress stands on it, with `repairQuests()` in `src/sim/quest-repair.ts`, as [Quests](quests.md#saves) describes. A save holding a quest at a higher revision than the build comes from a newer build and is a `SaveError` (`newerQuests`).

## Rescue

Some saves carry over at once, with no save screen. `carriesOnLoad()` in `src/three/save.ts` picks them by their `SaveError` code. One kind is a save whose minor format the steps cannot reach: a format older than the release steps, or one no build shipped. That is `outOfReach`. The other kind is a Chaos Highway save on a highway the generator no longer builds, or a run from before the highway. That is `mapChanged`. It keeps its progression and loses its place on the run. A save whose step names this build cannot place is `unknownStep`, as Migration details describes. A Roaming save on an older bake of Icarus is no error: load moves it onto the new bake. Positions scale with the map size, and fog is resampled at the same scale. A truck on blocked ground moves to the nearest free spot, and NPC routes are cleared. Broken props stand again. Stocks, claims, surveys, jobs and memories that name a prop the new bake lacks are dropped, and a contract on one lapses with no penalty, except a claim whose part the player already holds. Boot tries the carry before it shows the save screen, and a carry that throws shows the save screen with Migrate save turned off. A save that names the wrong kind of map for its mode contradicts itself, so it stays `otherMap` and goes to the save screen. Boot does not write the carried world, so the stored save stays downloadable until the next save.

A save that cannot load for another reason, from the wrong kind of map for its mode, another major format, a newer minor format or quest revision, a migration step that throws, or with an invalid shape, shows the save screen. Quest state that no longer fits never sends a save here, since load repairs it in place. The save screen shows the `SaveError` code as it is, untranslated, and offers Migrate save, New game, which opens the setup screen in `src/ui/new-game.ts` like every New game route (the Menu, the death screen and this one), or Download save, which hands the player the stored save as a file to attach to a bug report. `src/three/save-rescue.ts` reads the raw save defensively, `carriedWorld()` in `src/sim/world.ts` rebuilds the world on the current map from a new game and carries the skill ranks, XP, perks, the paint job slot by slot, money, truck, parts with wear, garage storage, cargo, fuel, supplies, discovered places, valid world settings, the journal notes and the quest variables that `repairQuests()` keeps, parks the truck on a town pad and refunds what no longer fits, and `src/ui/save-screen.ts` shows the choice. An old paint job id maps as step 93 to 94 does, a retired color maps as step 94 to 95 does, and an unknown slot id keeps its standard color. The reader holds its own copies of the old forms of these fields, like money before cents, skills before ranks and renamed notes and quest variables, so it reads a save of any minor format without the steps. A part or good id in `RETIRED_PRICES_RESCUE` becomes its price in cash. Other unknown ids, notes, quests and world variables are lost. An open quest closes, and the player can start it again. The rescue writes the new save at once.

When the carry cannot run, or the world it builds fails the check, the save screen says the save does not fit this version and offers only New game and Download save. Boot never throws anything but a `SaveError` for a stored save, so no stored save reaches the crash screen.

A Chaos Highway run goes back to the start of the stretch it was on. The start is outpost `window`, or outpost `window + 1` when the run was paid there and waits for the road. The rescue builds the current highway at that window, and `startRun()` parks both trucks on that outpost's pad, waiting for the road, with the stretch's groups planned fresh and the outpost stock rolled again. It keeps the run's earned money, wrecks, trucks sold at that outpost and discovered outposts. The hauler's parts, damage and cargo go through the same carry as the gun truck, and its fuel and supplies are kept. Every vehicle, part and item gets a new id. A run with no readable window or hauler throws, since a fresh run would lose it. A save whose run older rules dropped to null gets a fresh run with its truck.

## Migration details

- The save format has a major and a minor number. A save loads only in its own major format. Load carries it from its minor format to the current one.
- The saved shape is everything in `World` that `saveOf()` writes. A change to a type it reaches in `src/sim/types.ts` changes the shape. A rename or removal of a content id in `src/data/`, like a part or good id, changes it too.
- Steps come in two kinds. A release step in `RELEASE_STEPS` carries a save from one shipped format to the next. A tiny step in `TINY_STEPS` carries a save one minor format on, and tiny steps start at `TINY_FROM`, the newest shipped format they have not been folded past. Load runs the release steps from the save's format, then the tiny steps. A save at a format between two shipped ones is out of reach and goes to the rescue.
- Each tiny step has a name, like `withCrimes`, written once and never changed. A minor number says how many steps a save went through, not which ones, and two branches can give one number to two different steps. So a save also writes `steps: { from, names }`: `from` is the writing build's `TINY_FROM`, and `names` lists its tiny steps. Each release step holds `names`, the tiny step names it absorbed, or `null` for folds made before names.
- A save with `steps` whose minor is not `from` plus the number of names contradicts itself and is `noFormat`.
- Load resolves a save with `steps` from its `from`. At `TINY_FROM`, every name must be a tiny step name, and load runs each tiny step the list lacks, in code order. At an older anchor, the release step starting there must have names: a list that starts with all of them already holds that release step, so load skips it and resolves the rest from its `to`, and an empty list takes the minor number path. Anything else, like a name this build does not know or a list cut short between two shipped formats, is `unknownStep` and carries on load. A save with no `steps`, from before named steps, takes the minor number path, and only that path has the `newer` check.
- The minor format is `TINY_FROM` plus the number of tiny steps. It never goes down, and a new tiny step raises the game version's y. A major bump empties both lists and raises the game version's x. Saves of an older major carry over through the save screen, which keeps progression and rebuilds the world. A new map file needs no bump, since load moves a Roaming save onto the new bake.
- A new field gets what a new game would give, or a value derived from saved data. A renamed field or id moves. A removed field or id is dropped, and removed parts or goods turn into their sale value in cash.
- Each tiny step's test feeds it a trimmed save of format N from `src/three/save-fixtures/`, holding the fields the step changes, and checks the result.
- `src/three/save-fixtures/anchors/` holds full saves played on the build at each shipped tag, one Roaming and, where the mode existed, one Chaos Highway save. `save-folds.test.ts` checks each release step's output on them against a recorded hash, and writes the world to `tmp/release-steps/` on a mismatch.
- Some stocks come from the map rather than the save. `loadWorld()` calls `stockOldSpots()`, which rolls every old-world loot spot stock a save lacks, so a save from before old spots loads with all of them. The old spot picks and survey sites are files baked from the map, and `npm run old-spots` can rewrite them under the same map hash. So every same-map load runs `fitBake()` in `src/sim/map-repair.ts` first. It drops the old spot stocks the picks no longer hold and lapses their claims. It also drops survey points whose site is gone, and a held survey with no point left counts as done. A past survey with no point left leaves the journal's Past list.
- Release step 25 to 61 turns saved English into the sim's text ids. Goal reasons become `GoalReason` ids through a copy of every old phrase in `src/three/save-text-2-19.ts`, and a phrase no table knows becomes `'legacy'`, shown as Busy, so an old save still loads. An open call's line becomes its `LineId`, and a call on an unknown line hangs up. Trucks and bounty contracts lose their names, and the last turn's text events go, since nothing reads them after a load. See [Text and languages](text.md).
- `ChaosHighwayRun.hauler` holds the hauler's vehicle id and the turn its alarm ends, and its vehicle is saved with the others.
- Step 82 to 83 gives every shop a goods stock from its old pressure, drops board hauls of goods a shop no longer trades and the free haul goals, and empties the road news.
- Step 83 to 84 sets `restockAt` to the saved turn for a Bowl or Nose shelf with no stock engine, so the next turn rolls a shelf with the staple engine.
- Step 84 to 85 adds `world.sunward`, `{ collapsed: null, night: null, lastHunt: null }` in Roaming and `null` on Chaos Highway, and the player's Sunward standing at its start value. The Hollow's props are never saved, so an old save gains them at load, and the order fills its bays by day while the player is away.
- Step 85 to 86 moves the `brain.home` of each Sunward car from a bay of the round-1 Hollow at (356, 334) to the fort bay of the same index, from its own copies of both bay lists, and moves no car. A home that matches no old bay throws.
- Step 86 to 87 gives an open Sunward night `offered: []`, the trucks that gave the order their word that night.
- Release step 61 to 62 moves an open session at `wagon_seven` `start.hub` to `start` and at `wagon_bench` `bench.hub` to `bench.report`, so a load replays the scene before its hub.
- Step 87 to 88 sets `heading` to null on every `follow` step of an open directions answer, so it reads with the words it had before headings.
- Step 90 to 91 adds `player.pastContracts: []`. Each record holds a full copy of a finished `Contract`, so a later step that changes a contract's shape maps `player.pastContracts` as well as `player.contracts` and the shop boards. The saved shape of a new game holds an empty list and will not catch a missed one.
- Step 93 to 94 moves a saved hauler from the middle of the rigid semi onto its tractor, `TRACTOR_AHEAD` tiles ahead along its heading, and gives it `bend: 0`. Load then checks every rig and rig hulk through `checkRigs()` in `src/sim/rig.ts`: a rig with no `bend`, a bend past its limit or a rigid truck with a bend fails with `SaveError('invalidWorld')`. The step lives in `src/three/save-steps-late.ts` with the other late steps.
- Step 94 to 95 gives the player the `standard` paint job.
- Step 95 to 96 turns the paint job id into `{ body, cab, gear }` palette ids from its own copy of the old presets: `standard` is tan, olive and tan, and plum, lavender, mint and rose keep their body on body and gear with the nearest palette cab. `bone` and any other id become the standard paint.
- Step 96 to 97 moves each retired palette id in `player.paint` to a current color from its own table: plum and wine to oxblood, rose to sand, pink, lavender and mint to chalk, navy to slate. A current id passes, and any other value becomes that slot's standard color.
- Step 97 to 98 gives each truck with held turns a `strandedAt` anchor at its saved position.
- Step 98 to 99 changes no data. It marks the new `helpRefused` state kind, the `askHelp` topic and the `answeredCall` goal reason.
- Step 99 to 100 changes no data. It marks the `firstAid` job kind.
- Step 104 to 105 changes no data. It marks the `failedContract` deed.
- Step 105 to 106 changes no data. It marks the `late` ending, the `overdue` contract event, the `embezzled` offense and the shop case issuer.
- Step 103 to 104 drops every `fetch` and `bounty` contract from the shop boards, `player.contracts` and `player.pastContracts`. A held bounty already met pays its reward into `player.money` first. `player.perks` maps `bountyTalk` to `bountyHunter`, and `readCarried()` maps the perk the same way.
- Step 106 to 107 moves the `brain.home` of each Sunward car, and any goal destination at a bay, from the bay of the same index of the Hollow at (304, 516) to the laager bay of the same index, from its own copies of both bay lists, and moves no car. A home that matches no old bay throws.
- Load runs `settleOffHollow()` on a same-map load: a truck whose body overlaps a Hollow obstacle moves to a free spot nearby, like the move after a rebake.
- Step 109 to 110, `withCaseRestitution`, gives every case `restitution: 0` and `known: true`, since those players already saw the old filing line, and every `witnessed` memory `restitution: 0`.
- Step 110 to 111, `withCasePosse`, gives every saved case `posse: 'lone'`, so an old case waits for one Marshall.
- Step 112 to 113, `withRefitQueues`, gives every saved refit job `queue: []`.
- Step 101 to 102 adds `world.crimes: []` and the player's Marshalls standing at 0. It also marks the `witnessed` memory, the `pursue` goal, the `bountyHunt`, `atPost`, `caseClosed` and `huntGaveUp` reasons, the `bountyStop` state and the Marshalls faction, template, trait and site.
- Step 109 to 110 renames the mode and the run again, to the name players see: `setup.mode: 'furyRoad'` becomes `'chaosHighway'` and the world key `furyRoad` becomes `chaosHighway`, with the run kept as it is and null kept in Roaming. The save list and the rescue read a raw save, so they map the old mode with the step's `chaosHighwayMode_107_108()`, and the rescue reads the run from `furyRoad` in a save before format 108. Old run log records keep `mode: 'furyRoad'` in their `session` line, since the sim never reads them back.
- Step 48 to 49 renames the mode from its first name: `setup.mode: 'gauntlet'` becomes `'furyRoad'` and the world key `gauntlet` becomes `furyRoad`. The run inside is kept as it is. A run saved on the first highway then misses its map hash, since the highway's rules are at version 2, and goes to the rescue, which starts a new Chaos Highway run with its truck.
- `src/three/save-shape.json` records the saved shape of a new game under the current format. A test fails when the shape changes without a new format. `npm run save:shape` refuses to record a new shape under an old format. It also records the saved quest variable names and checkpoints, and refuses a lost one under an old format unless the quest's revision rose. It records each quest's revision and links too, and refuses a link change old saves may not follow, as [Changing a shipped quest](../writing/quests.md#changing-a-shipped-quest) describes.
- The game version comes from the commit that first records the current format in `save-shape.json`. Git's search skips merge commits, so a new format must land in a plain commit, not in a merge resolution.

## Folding tiny steps

Players hold saves only at formats a `release-*` or `hotfix-*` tag shipped. Saves of dev and candidate builds at other formats carry over through the rescue once their steps fold. `save-anchors.test.ts` reads the tags and fails when a format shipped in the last 10 releases loads through no step, when a release step starts at a format no tag shipped, when a release step is older than the last 10 releases, or when a second shipped format sits above `TINY_FROM`.

After a ship with a new format F, fold on `dev`, never on the release branch:

1. Make full saves at F on a checkout of the tag. Play a new Roaming game and a Chaos Highway run for 2 game days with the harness bots of `src/sim/progression/record.ts`, and write each `saveOf()` envelope to `save-fixtures/anchors/2-F-roaming.json` and `2-F-highway.json`.
2. Copy `save-migrations.ts` and the files it imports to `tmp/` as the old chain.
3. Write one release step from `TINY_FROM` to F, with `names` set to the names of the tiny steps it folds, in order. Merge the tiny steps between them: drop work on fields a later step drops anyway, and steps that no save at `TINY_FROM` can reach.
